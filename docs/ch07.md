## 1. Kubeflow Notebooks

### 1.1 왜 노트북 서버인가

데이터 분석 환경에는 서로 부딪히는 요구가 있다.

- 큰 데이터셋을 다루려면 **데이터 가까이에서** 돌아야 한다.
- GPU·대용량 메모리처럼 **비싼 자원에 수시로 대화형 접근**이 필요하고, 쓰지 않을 때는 내려야 한다.
- 실험 환경이 **배포 환경과 같아야** 하고, 버전 관리와 CI/CD가 적용돼야 한다.

Kubeflow Notebooks는 브라우저에서 Jupyter, VS Code(code-server), RStudio를 띄워 주면서, 노트북 이미지를 **파이프라인 이미지와 같은 CI**로 빌드할 수 있게 해 이 요구를 한 번에 맞춘다.

### 1.2 노트북 서버 설정 항목 (7.1.1~7.1.3)

| 항목 | 내용 | 주의 |
|---|---|---|
| Namespace | 노트북이 뜰 네임스페이스 | 리소스 할당량, 볼륨, 시크릿이 여기에 묶인다 |
| Image | Jupyter / code-server / RStudio 이미지 | 커스텀 이미지 추가 가능(1.4) |
| CPU / Memory | K8s requests·limits와 같다 | 메모리 한도를 너무 낮게 잡지 않는다 |
| GPUs | GPU·TPU 개수 | 비싸고 다른 파드를 막는다. **유휴 시 종료 규칙(culling)** 을 반드시 둔다 |
| Workspace volume | `/home/jovyan`에 자동 마운트 | 기본 StorageClass로 생성, 환경·설정 파일이 남는 곳 |
| Data volume | 기존 PVC를 런타임에 마운트 | 데이터셋 공유 용도 |
| Configurations | 네임스페이스의 **PodDefault** 선택 | 아래 1.3 |
| Affinity / Tolerations | 특정 노드(GPU 등)에 배치 | ConfigMap으로 선택지를 제한 가능 |
| Shared memory | `/dev/shm` 활성화 | 분산 학습, 메모리 캐시 데이터 로더에 유리 |

Launch하면 워크스페이스 PVC 생성 → 스케줄링 → 이미지 pull 순으로 진행되고, 파드에는 메인 컨테이너와 함께 **Istio 사이드카**가 붙는다(정식 설치 기준). 실체는 `notebooks.kubeflow.org` CRD의 `Notebook` 리소스이고, 컨트롤러가 **StatefulSet + Service**로 만든다.

### 1.3 PodDefault: 파드에 설정 주입

노트북 파드 라벨이 PodDefault의 `selector`와 맞으면 웹훅이 env·볼륨·시크릿 등을 주입한다.

```yaml
apiVersion: kubeflow.org/v1alpha1
kind: PodDefault
metadata:
  name: add-ml-env
  namespace: kubeflow-user
spec:
  desc: add MLflow and KFP endpoints        # UI 선택지에 표시되는 설명
  selector:
    matchLabels:
      add-ml-env: "true"
  env:
    - name: MLFLOW_TRACKING_URI
      value: http://mlflow-service.mlflow.svc.cluster.local:5000
    - name: KF_PIPELINES_ENDPOINT
      value: http://ml-pipeline.kubeflow.svc.cluster.local:8888
```

- 책 listing 7.1은 프록시 변수(`http_proxy` 등)와 `MLFLOW_TRACKING_URI`를 주입한다. 이 환경에서는 프록시를 빼고 MLflow·KFP 주소만 넣었다.
- `MLFLOW_TRACKING_URI`가 있으면 MLflow 클라이언트가, `KF_PIPELINES_ENDPOINT`가 있으면 `kfp.Client()`가 **인자 없이** 바로 접속한다.
- 자격증명, 특수 설정, 볼륨 마운트까지 확장할 수 있다. 경로와 PVC 이름을 **클러스터 관리자가 통제**하면서 사용자에게는 체크박스로만 노출하는 방식이다.
- PodDefault를 바꾸면 **파드를 다시 만들어야** 반영된다(웹훅은 파드 생성 시점에만 동작).

### 1.4 메뉴 커스터마이징 (7.1.4)

노트북 생성 화면의 선택지는 `kubeflow` 네임스페이스의 `jupyter-web-app-config-*` ConfigMap(`spawner_ui_config.yaml`)에서 온다. 각 항목에 `value`(기본값)와 `readOnly`(사용자 수정 불가)가 있다.

```yaml
spawnerFormDefaults:
  image:
    value: kubeflownotebookswg/jupyter-scipy:v1.6.1      # 기본 Jupyter 이미지
    options:                                              # 드롭다운 목록
      - .../jupyter-tensorflow:2.6.0
      - .../jupyter-pytorch:1.9.0
  imageGroupOne: [kubeflownotebookswg/codeserver-python:v1.6.1]   # code-server
  imageGroupTwo: [kubeflownotebookswg/rstudio-tidyverse:v1.6.1]   # RStudio
  affinityConfig:
    value: ""
    options:
      - configKey: small-cpu-selector
        displayName: small-cpu-node
        affinity: {nodeAffinity: ... key: compute, In: [small]}
      - configKey: xl-cpu-selector
        displayName: xl-cpu-node
        affinity: {nodeAffinity: ... key: compute, In: [xl]}
```

- **이미지 목록을 CD 파이프라인이 관리**하게 하면, 승인된 이미지만 노트북에 노출하는 흐름을 쉽게 만들 수 있다. `readOnly`로 목록 밖 이미지 입력을 막는다.
- 어피니티는 노드를 **끌어당길** 뿐이라, 저성능 노드가 차면 고성능 노드로도 간다. 고성능 노드를 정말 막으려면 **테인트 + 톨러레이션**을 함께 쓴다.

### 1.5 커스텀 노트북 이미지 (7.1.5)

커스텀 이미지는 **베이스 이미지 + 런타임 의존성 + Jupyter/code-server 런타임 + Kubeflow 호환 실행 설정**의 계층으로 구성된다(그림 7.6). 프로젝트 저장소의 멀티스테이지 Dockerfile이 베이스 이미지를 인자로 받아 Jupyter나 code-server 이미지를 만든다. 조직에 배포할 때는 Dockerfile을 검토하고 이미지 크기를 줄인다.

### 1.6 이 환경에서: 경량 설치 (필수 실습 아님)

실습 환경은 **KFP standalone 2.4.1**이라 Central Dashboard, Jupyter Web App, Istio, Profile이 없다. 그래서 **notebook-controller와 PodDefault 웹훅만** 설치하고 `Notebook`·`PodDefault` CR을 직접 만들어 7.1.1~7.1.3을 재현했다.

| 구성 요소 | 이미지 | 비고 |
|---|---|---|
| notebook-controller | `ghcr.io/kubeflow/notebooks/notebook-controller:v1.11.0` | `USE_ISTIO=false`, culling 끔 |
| poddefaults-webhook | `ghcr.io/kubeflow/dashboard/poddefaults-webhook:v2.0.0` | cert-manager 자체 서명 인증서 |
| 노트북 이미지 | `ghcr.io/kubeflow/kubeflow/notebook-servers/jupyter-scipy:v1.11.0` | |

```bash
kubectl apply --server-side --force-conflicts -f pdw.yaml   # PodDefault CRD + 웹훅
kubectl apply --server-side --force-conflicts -f nbc.yaml   # Notebook CRD + 컨트롤러
kubectl get crd | grep -E 'notebooks|poddefaults'
```

설치에서 알아 둘 점:

- KCD 26.03.1에서 PodDefault 웹훅 매니페스트는 `applications/dashboard/upstream/poddefaults-webhooks`에 있다(notebooks-v1 아래가 아니다).
- 웹훅의 `namespaceSelector`가 **`app.kubernetes.io/part-of=kubeflow-profile` 라벨이 붙은 네임스페이스만** 대상으로 한다. Profile 컨트롤러가 없으니 네임스페이스에 라벨을 직접 붙여야 주입된다.
- `Notebook` CR의 `metadata.labels`가 파드로 전파되고, 이것이 PodDefault `selector`와 맞아야 주입된다.
- 웹훅 `failurePolicy: Fail`이라, 웹훅 파드가 죽으면 **라벨 붙은 네임스페이스의 모든 파드 생성이 막힌다**.

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: kubeflow-user
  labels:
    app.kubernetes.io/part-of: kubeflow-profile   # 웹훅 대상이 되려면 필수
---
apiVersion: kubeflow.org/v1
kind: Notebook
metadata:
  name: test-nb
  namespace: kubeflow-user
  labels:
    add-ml-env: "true"                             # PodDefault selector와 일치
spec:
  template:
    spec:
      containers:
        - name: test-nb
          image: ghcr.io/kubeflow/kubeflow/notebook-servers/jupyter-scipy:v1.11.0
          resources:
            requests: {cpu: "500m", memory: 1Gi}
            limits: {cpu: "2", memory: 4Gi}
          volumeMounts: [{name: workspace, mountPath: /home/jovyan}]
      volumes:
        - name: workspace
          persistentVolumeClaim: {claimName: test-nb-workspace}   # 5Gi PVC 별도 생성
```

결과 확인:

```bash
kubectl get notebook,poddefault -n kubeflow-user
kubectl get sts,pod,pvc -n kubeflow-user           # sts/test-nb 1/1, pod/test-nb-0 Running
kubectl describe pod -n kubeflow-user -l notebook-name=test-nb
#   NB_PREFIX:              /notebook/kubeflow-user/test-nb
#   MLFLOW_TRACKING_URI:    http://mlflow-service.mlflow.svc.cluster.local:5000
#   KF_PIPELINES_ENDPOINT:  http://ml-pipeline.kubeflow.svc.cluster.local:8888
```

- 노트북 안에서 `kfp.Client()`를 **인자 없이** 호출해 실험 2개, 파이프라인 4개를 조회했고, MLflow `/health`와 JupyterLab API도 200이었다.
- 접속은 `kubectl -n kubeflow-user port-forward svc/test-nb 18888:80` 후 `http://localhost:<포트>/notebook/kubeflow-user/test-nb/lab`. **`NB_PREFIX` 경로가 없으면 404**다.
- 이미지에 `mlflow`, `boto3`가 없어 `pip install`이 필요하다. 설치물은 워크스페이스(`/home/jovyan`)에 남는다.
- 노트북 파드가 최대 4Gi를 쓰므로(서버 가용 메모리 약 7GiB) 쓰지 않을 때는 `kubectl delete notebook`으로 내린다. PVC를 지우면 워크스페이스 데이터도 사라진다.

## 2. KFP 데이터 전달

### 2.1 왜 어려운가

KFP의 컴포넌트는 **각자 별도의 K8s 파드**에서 실행된다. 메모리를 공유하지 않으므로 앞 단계의 결과를 뒤 단계로 넘기는 장치가 필요하고, 이 부분에서 처음 쓰는 사람도 숙련자도 자주 헷갈린다.

| 전달 방식 | 쓰는 법 | 어디에 저장되나 | 알맞은 대상 |
|---|---|---|---|
| **값(parameter)** | 함수 반환값 `-> str/int`, 받는 쪽은 `.output` | 다음 파드의 명령 인자·annotation, MLMD | 작은 문자열·숫자 |
| **경로(artifact)** | `Output[Artifact/Dataset]`의 `.path`에 파일을 쓴다 | 오브젝트 스토리지(MinIO `mlpipeline` 버킷) | 데이터셋, 모델 등 큰 데이터 |
| 메트릭 | `Metrics`, `ClassificationMetrics` | **MLMD(MySQL `metadb`)에만**, 파일 없음 | 평가 지표 |

아티팩트 경로는 `/minio/mlpipeline/v2/artifacts/<파이프라인>/<run_id>/<태스크>/<실행UUID>/<이름>` 형태다. 런처가 만든 로컬 경로이고, 실제로는 MinIO에 같은 키로 올라간다. 디렉터리 아티팩트는 `<이름>/jokes.txt`처럼 **키 접두사**로 저장된다.

### 2.2 시나리오 1: 단순 값 전달 (7.2.1)

농담 생성 → 단어 수 세기 → 결과 출력. 함수 세 개를 컴포넌트로 바꿔 잇는다.

```python
import kfp.dsl as dsl

@dsl.component(packages_to_install=["pyjokes"], base_image="python:3.11")
def generate_joke() -> str:
    import pyjokes              # import는 반드시 함수 안에서
    return pyjokes.get_joke()

@dsl.component
def count_words(input: str) -> int:
    return len(input.split())

@dsl.component
def output_result(count: int) -> str:
    return f"Word count: {count}"

@dsl.pipeline(name="joke-pipeline-values", description="simple pipeline demonstrating value passing")
def pipeline():
    generate_joke_op = generate_joke()
    count_word_op = count_words(input=generate_joke_op.output)
    output_result(count=count_word_op.output)
```

- **import는 함수 안에 둔다.** 함수 하나가 컨테이너로 패키징되므로 의존성이 함수 안에 캡슐화돼야 한다.
- 반환값은 컴포넌트의 `.output`이 되고, 이를 다음 컴포넌트 인자로 넘기면 DAG 의존성도 함께 생긴다.
- **책 listing 7.5에는 이름 오류가 있다.** `output_result = output_result(...)`로 함수를 같은 이름 변수로 덮어쓰고, `count_word`로 받은 뒤 `count_word_op`를 참조해 `NameError`가 난다. 위 코드는 고친 버전이다.

**컴포넌트에서 패키지를 쓰는 세 가지 방법**

1. `base_image`에 미리 설치된 이미지를 쓴다(경량 컴포넌트는 Python 3.5+ 필요).
2. `packages_to_install`에 적는다(위 `pyjokes`처럼). requirements.txt와 비슷하다.
3. 함수 안에서 `subprocess`로 `pip install`한다. 명시성이 떨어져 권장하지 않는다.

운영에서는 1번(이미지 고정)이 맞다. 2번은 **파드가 뜰 때마다 PyPI에서 설치**하므로 느리고, 외부망이 막힌 클러스터에서는 실패하며, 버전을 고정하지 않으면 재현성도 깨진다.

### 2.3 컴파일된 YAML 읽기: 코드 인젝션

컴파일 결과는 세 부분으로 나뉜다.

| 섹션 | 역할 |
|---|---|
| `components.comp-*` | 인터페이스: 타입이 지정된 입출력(`parameterType: STRING` 등) |
| `deploymentSpec.executors.exec-*` | 런타임: 이미지, 명령, **주입된 함수 코드** |
| `root.dag.tasks` | 워크플로: 태스크 간 연결(`taskOutputParameter`), 캐시 설정 |

실행자 하나(`exec-count-words`)의 `command`는 세 덩어리다.

```yaml
command:
- sh
- -c
- |                                  # ① pip 확인 후 kfp 런타임 설치 (+ packages_to_install)
  if ! [ -x "$(command -v pip)" ]; then python3 -m ensurepip || ...; fi
  PIP_DISABLE_PIP_VERSION_CHECK=1 python3 -m pip install --quiet 'kfp==2.9.0' '--no-deps' ...
```

- 함수 소스가 **명령 인자 문자열**로 들어가고, `executor_main`이 입력을 역직렬화해 함수를 부른 뒤 반환값을 출력으로 기록한다. 직렬화와 데이터 전달은 KFP가 처리한다.
- `{{$}}` 자리에 런타임에 **executor input(JSON)** 이 채워진다. 값 전달의 값도 여기 들어간다. 그래서 큰 값을 넘기면 명령 인자가 커져 터진다(2.4).
- 기본 베이스 이미지는 SDK 버전을 따른다. 이 환경(SDK 2.9.0)은 `python:3.8`, 책(2.11.0)은 `python:3.9`였다. **베이스 이미지를 지정하지 않으면 SDK를 올릴 때 런타임 Python이 바뀐다.**
- 컴파일된 YAML의 구조 확인은 `inspect_yaml.py`(실행자별 이미지, pip 블록, 주입 코드, 아티팩트 `schemaTitle` 출력)로 했다.

### 2.4 실습 결과: 값으로 어디까지 넘길 수 있나

환경: kind `book-env`, KFP 백엔드 2.4.1, SDK `kfp 2.9.0`(Python 3.11), 실험 `ch07-data-passing`, 모든 실행 캐시 OFF. 제출은 `submit.py <yaml> <run_name> key=value ...`(`enable_caching=False`로 실행 후 태스크 상태와 `[ch07]` 마커 로그 출력).

| 단계 | 실험 | 결과 | 관찰 |
|---|---|---|---|
| A1 | 값 전달 (listing 7.5 수정본) | 성공 | 농담 → 단어 수 → `Word count: N` |
| A2 | 경로 전달 `num_jokes=42 / 5` | 성공 | 539 / 72단어, 디렉터리 아티팩트가 MinIO 키 접두사로 저장 |
| A2b | 값 10KB, 60KB | 성공 | |
| A2b | 값 100KB | **실패** | `argument list too long`: 값이 파드 명령 인자에 들어감 |
| A2b | 값 1MB | **실패** | annotations 262,144바이트 초과로 다음 파드 미생성 |
| A2b | 값 10MB | **실패** | MLMD gRPC 4MB 한도 초과(10,240,924 > 4,194,304) |
| A2b | 경로 10MB, 200MB | 성공 | 200MB도 문제없음 |
| A3 | 책 코드 그대로 (`np.save`) | **실패** | `FileNotFoundError`: `np.save`가 `.npy` 확장자를 자동으로 붙임 |
| A3 | 수정본 (파일 핸들로 저장) | 성공 | `metadata`(samples, shape) 전달 확인 |
| A4 | 아티팩트 타입 7종 | 성공 | MLMD에 `system.*` 7종 등록, 메트릭 값 저장 |

값 전달은 크기에 따라 **세 겹의 한도**에 걸린다.

```text
~60KB   OK
100KB   커널 ARG_MAX(명령 인자 길이)           → argument list too long
1MB     K8s 오브젝트 annotations 256KiB 한도    → 다음 파드가 생성조차 안 됨
10MB    MLMD gRPC 메시지 4MB 한도              → ResourceExhausted
```

결론은 책과 같다. **"큰 데이터는 값이 아니라 경로로 넘겨라."** 경계는 대략 수십 KB이니, 문자열 하나라도 크기가 가변적이면(예: 농담 여러 개, JSON 리스트) 처음부터 아티팩트로 설계하는 편이 안전하다.

**A3 `np.save` 함정.** `np.save(path, arr)`은 경로가 `.npy`로 끝나지 않으면 확장자를 붙여 저장한다. KFP가 준 `out.path`에는 확장자가 없으니 실제 파일은 `<path>.npy`가 되고, 런처가 `<path>`를 업로드하려다 실패한다. `with open(out.path, "wb") as f: np.save(f, arr)`처럼 **파일 핸들로 저장**하면 해결된다. 라이브러리가 경로를 바꾸는 저장 함수(`np.save`, `torch.save` 일부 등)는 모두 이 방식으로 다룬다.

**결과 확인 위치**

| 무엇 | 어디서 |
|---|---|
| 실행 상태·로그 | `submit.py` 출력, `kubectl -n kubeflow logs -l pipeline/runid=<run_id> -c main` |
| MinIO 아티팩트 | `mlpipeline` 버킷 `v2/artifacts/<파이프라인>/<run_id>/...` |
| 메트릭·아티팩트 타입 | MySQL `metadb.Artifact` ⋈ `metadb.Type` (`uri like '%<run_id>%'`) |
| 값 전달 실패 원인 | 워크플로의 driver 메시지(annotations 초과), 파드 이벤트(argument list too long), 로그(ResourceExhausted) |
| UI | Runs → 실험 `ch07-data-passing` → 노드 클릭 시 입출력 미리보기, 좌측 Artifacts 메뉴는 MLMD 목록 |

> 정리 필요: run 14개와 완료된 파드, MinIO 아티팩트(200MB 포함)가 남아 있다.

## 정리하며

- Kubeflow Notebooks의 실체는 **`Notebook` CR → StatefulSet**과 **PodDefault 웹훅**이다. 대시보드 없이도 CR 두 개로 노트북 환경을 재현할 수 있었다.
- PodDefault는 "사용자는 체크박스만, 주소·자격증명·볼륨은 관리자가" 하는 구조다. 다만 웹훅이 `failurePolicy: Fail`이라 **웹훅 장애가 곧 해당 네임스페이스의 파드 생성 장애**가 된다.
- KFP는 함수 소스를 컨테이너 명령 인자에 주입해 실행한다. 이 구조 때문에 **값 전달은 명령 인자 크기의 제약**을 그대로 받는다. 이 환경에서는 100KB부터 실패했다.
- 큰 데이터는 처음부터 `Output[Artifact]` 경로로 설계하고, 저장 함수가 경로를 바꾸지 않는지(`np.save`) 확인한다.
- DevOps 입장에서 챙길 곳은 **웹훅 가용성과 인증서(cert-manager), 노트북 리소스 한도와 culling, 이미지 고정(`packages_to_install`보다 `base_image`), 기본 베이스 이미지의 SDK 의존성, 파이프라인이 남기는 아티팩트와 MLMD 데이터 정리**다.
