# CH5. Kubeflow Pipelines 시작: 설치와 첫 파이프라인

## 핵심 요약

- 4장 끝에서 남은 수동 단계(재학습, materialize)를 자동화하려면 **파이프라인 오케스트레이터**가 필요하다. 이 책의 선택은 Kubeflow Pipelines(KFP)다.
- Kubeflow 전체(대시보드, 노트북, KServe, 인증 등)는 노트북 한 대에 올리기엔 무겁다. 파이프라인 기능만 쓰는 **KFP standalone**으로 설치했다.
- 설치는 두 단계다. **CRD 등 cluster-scoped 리소스를 먼저**, 그다음 `platform-agnostic` 환경을 적용한다.
- 첫 파이프라인은 덧셈 컴포넌트 두 개를 잇는 `week01-hello`다. 첫 단계의 **출력이 둘째 단계의 입력**으로 넘어가는 것을 로그로 확인했다.

> 이 문서는 KFP standalone 설치와 첫 파이프라인 실행까지만 다룬다. ML 파이프라인(MLflow·Feast 연동, 재학습 자동화)은 이어서 채운다.

## 1. 이 장에서 하는 일

```mermaid
flowchart LR
  CRD[CRD 설치] --> KFP[KFP standalone 설치] --> UI[UI 노출] --> DSL[파이프라인 작성·컴파일] --> RUN[실행·로그 확인]
```

| 단계 | 하는 일 |
|---|---|
| CRD | `cluster-scoped-resources`를 먼저 적용하고 CRD가 established 될 때까지 대기 |
| 설치 | `env/platform-agnostic` kustomize 적용 (버전 2.17.3) |
| UI | `ml-pipeline-ui` 서비스를 NodePort로 변경 |
| 작성 | `@dsl.component`, `@dsl.pipeline`으로 정의하고 YAML로 컴파일 |
| 실행 | KFP 클라이언트로 run 생성, 완료까지 대기 |

## 2. KFP standalone 설치

```bash
export PIPELINE_VERSION=2.17.3

# 1) CRD 등 cluster-scoped 리소스 먼저
kubectl apply -k "github.com/kubeflow/pipelines/manifests/kustomize/cluster-scoped-resources?ref=$PIPELINE_VERSION"
kubectl wait --for condition=established --timeout=60s crd/applications.app.k8s.io

# 2) 본체 설치
kubectl apply -k "github.com/kubeflow/pipelines/manifests/kustomize/env/platform-agnostic?ref=$PIPELINE_VERSION"

# 3) UI를 NodePort로
kubectl -n kubeflow patch svc ml-pipeline-ui --type merge -p \
  '{"spec":{"type":"NodePort","ports":[{"port":80,"targetPort":3000,"nodePort":30008}]}}'
```

- **순서가 중요하다.** CRD가 없는 상태에서 본체를 적용하면 커스텀 리소스를 만들 수 없다. 그래서 먼저 설치하고 `kubectl wait`로 등록을 확인한다.
- `ref=$PIPELINE_VERSION`으로 버전을 고정한다. 클러스터에 `latest`를 그대로 적용하지 않는다.
- 네임스페이스는 `kubeflow`다. UI 서비스는 `ml-pipeline-ui`(80 → 3000)이고, 위 패치로 NodePort 30008에 노출된다.
- 실행 예에서 클라이언트는 `http://localhost:8888`로 접속한다. NodePort와 이 주소 사이는 포트 포워딩 등으로 이어 둔 구성으로 보이며, 접속 경로는 환경에 맞게 정한다.

## 3. 첫 파이프라인

```python
from kfp import dsl, compiler

@dsl.component(base_image="python:3.11-slim")
def add(a: float, b: float) -> float:
    print(f"{a} + {b} = {a + b}")
    return a + b

@dsl.pipeline(name="week01-hello")
def pipeline(x: float = 1.0, y: float = 2.0):
    first = add(a=x, b=y)
    add(a=first.output, b=10.0)

compiler.Compiler().compile(pipeline, "hello_pipeline.yaml")
```

| 요소 | 역할 |
|---|---|
| `@dsl.component` | 파이썬 함수 하나를 **컨테이너로 실행되는 단계**로 만든다. `base_image`로 실행 이미지를 정한다 |
| `@dsl.pipeline` | 단계들을 어떻게 잇는지 정의한다. 매개변수(`x`, `y`)와 기본값을 가진다 |
| `first.output` | 앞 단계의 출력을 뒤 단계의 입력으로 연결한다. 이 연결이 곧 **의존 관계**가 된다 |
| `Compiler().compile` | 파이프라인을 YAML(IR)로 컴파일한다. 이 파일을 UI에 올리거나 클라이언트로 제출한다 |

### 3.1 실행

UI에 업로드하지 않고 KFP 클라이언트로 바로 실행했다.

```python
import kfp
client = kfp.Client(host="http://localhost:8888")
run = client.create_run_from_pipeline_package("hello_pipeline.yaml", arguments={"x": 3, "y": 4})
print("state:", client.wait_for_run_completion(run.run_id, timeout=600).state)   # SUCCEEDED
```

- 컴파일(`pip install kfp` 필요)과 제출을 스크립트로 묶으면 CI에서 같은 흐름을 그대로 쓸 수 있다.
- `arguments`로 매개변수 기본값을 덮어쓴다(여기서는 `x=3`, `y=4`).

## 4. 실행 결과 확인

```bash
kubectl -n kubeflow get pods -l workflows.argoproj.io/workflow --sort-by=.metadata.creationTimestamp
```

```text
week01-hello-...-system-dag-driver-...         0/2   Completed
week01-hello-...-system-container-driver-...   0/2   Completed
week01-hello-...-system-container-impl-...     0/2   Completed
week01-hello-...-system-container-driver-...   0/2   Completed
week01-hello-...-system-container-impl-...     0/2   Completed
```

| 파드 | 의미 |
|---|---|
| `system-dag-driver` | 파이프라인 전체(DAG)를 시작하고 흐름을 관리 |
| `system-container-driver` | 컴포넌트 단계 하나를 실행하기 전 입력·설정을 준비 |
| `system-container-impl` | 컴포넌트 코드가 **실제로 실행되는** 파드 |

- 컴포넌트가 두 개라서 driver/impl 쌍이 두 번 나타난다. 단계마다 파드가 별도로 뜨므로, 단계가 많아지면 파드 수와 이미지 pull 비용도 함께 는다.
- 파드가 `0/2 Completed`로 보이는 것은 컨테이너 2개가 정상 종료됐다는 뜻이다.

값 전달은 로그로 확인했다.

```bash
kubectl -n kubeflow logs <container-impl 파드> -c main | grep ' = '
# 7.0 + 10.0 = 17.0
```

첫 단계가 `3 + 4 = 7`을 계산하고, 둘째 단계가 그 출력을 받아 `7 + 10 = 17`을 계산했다. 단계 사이의 값 전달이 **KFP를 통해** 이루어진 것이다.

## 5. 주의할 점

| 증상 | 원인 | 대응 |
|---|---|---|
| 파드가 `exec format error`로 종료 | Apple Silicon에서 일부 KFP 구성 요소 이미지가 amd64 전용일 수 있다 | Docker Desktop의 x86 에뮬레이션(Rosetta) 설정부터 확인 |
| 본체 적용 시 CRD 관련 오류 | cluster-scoped 리소스를 먼저 설치하지 않음 | 순서대로 설치하고 `kubectl wait`로 확인 |

---

## 정리하며

- KFP standalone은 파이프라인 기능만 올리는 **가벼운 설치 경로**다. 개인 환경이나 스터디에 알맞다.
- 파이프라인은 **함수(컴포넌트) + 연결(`.output`) + 컴파일 + 제출**로 이루어진다. 컴파일 결과가 파일이라 코드와 함께 버전 관리하고 CI에서 제출할 수 있다.
- 단계마다 별도 파드가 뜨므로, 4장의 학습·등록·materialize를 단계로 나누면 각 단계의 입출력과 이미지를 명확히 정해야 한다.
- DevOps 입장에서 챙길 곳은 **버전 고정, 설치 순서, UI 노출 방식(NodePort 여부), 아키텍처별 이미지 호환성**이다.
- 다음 단계는 4장에서 만든 MLflow와 Feast를 이 파이프라인 단계로 옮겨 재학습과 배치 예측을 자동화하는 것이다.
