# CH8. 노드 기능 선택과 파드 배치: 쿠버네티스 스케줄링

## 핵심 요약

- 8장은 **파드를 어느 노드에 올릴 것인가**를 다룬다. 크게 두 축이다.
  - **노드 쪽**: Arm, GPU, Spot처럼 특성이 다른 노드를 **고르거나 피한다**(nodeSelector, Node Affinity, Taint/Toleration).
  - **파드 쪽**: 파드끼리 **흩어 놓거나 모아 놓는다**(Topology Spread, Pod Affinity/Anti-Affinity).
- 쿠버네티스는 한 노드에 여러 파드를 촘촘히 채우는 **빈 패킹(bin-packing)** 으로 비용을 아끼지만, 그 대가로 **단일 장애 지점**이 생긴다. 복제본을 노드·존에 분산하는 것이 이 장의 핵심 처방이다.
- **Taint만으로도, 라벨만으로도 노드 전용화는 안 된다.** 전용 노드 그룹은 노드에 **Taint + 라벨**, 파드에 **Toleration + nodeSelector**를 모두 걸어야 완성된다. Toleration은 "올라가도 된다"일 뿐 "거기로 가라"가 아니다.
- **선호(preferred) 규칙은 조심한다.** 스케줄러는 기존 노드의 남는 자리를 먼저 쓰기 때문에 오토스케일러가 선호 노드를 늘려 줄 기회가 없다. 책은 `PreferNoSchedule`도 권하지 않는다.
- 토폴로지 분산은 **스케줄링 시점 제약**이다. 이미 뜬 파드는 안 움직이므로 재배치하려면 롤아웃을 다시 해야 한다.
- 규칙이 안 먹는 것 같으면 먼저 **soft 규칙을 required로 바꿔 검증**하고, Pending이면 **파드를 describe**해서 이벤트를 본다.
- 7장 노트북 서버의 Affinity/Tolerations(GPU 노드 배치)가 바로 이 장의 내용이다.

---

## 들어가며

지금까지는 노드를 모두 같은 것으로 취급했다. 하지만 실제 클러스터에는 성격이 다른 노드가 섞여 있다.

| 노드 특성 | 예시 | 파드가 신경 쓸 이유 |
|---|---|---|
| CPU 아키텍처 | x86 / Arm | 이미지가 Arm을 지원해야 한다 |
| 가속기 | GPU | 비싸서 GPU 워크로드만 써야 한다 |
| 프로비저닝 모델 | 일반 / Spot | Spot은 갑자기 회수될 수 있다 |
| OS | Linux / Windows | 이미지가 OS에 묶인다 |

관리형 플랫폼이 저수준 프로비저닝을 대신해 줘도 결국 워크로드는 어떤 머신 위에서 돈다. 그래서 필요할 때 **노드 특성을 골라 쓰는 방법**이 필요하다.

반대편에는 **빈 패킹**이 있다. 여러 컨테이너를 같은 하드웨어에 올리면 비용이 줄고, 옆 파드의 남는 용량을 일시적으로 빌려 쓰는 **버스트**도 된다. 단점은 **그 노드가 죽으면 같이 죽는다**는 것이다.

## 1. 노드 기능 선택 (8.1)

노드 특성은 **노드 라벨**로 구분하고, 파드는 **nodeSelector** 또는 **nodeAffinity**로 원하는 라벨을 표현한다.

### 1.1 nodeSelector (8.1.1)

가장 단순한 방법이다. 예를 들어 Arm 노드(`kubernetes.io/arch: arm64`)에서만 돌리려면 다음과 같다.

```yaml
spec:
  nodeSelector:
    kubernetes.io/arch: arm64
```

- `kubernetes.io/arch` 같은 **잘 알려진(well-known) 라벨**은 공급자가 달라도 일관되게 쓰도록 오픈소스에서 정의한다.
- 라벨을 요구하는 것은 첫 단계일 뿐이고, **그 라벨의 노드를 실제로 만드는 일은 플랫폼 몫**이다. 자동 모드의 GKE는 라벨만 걸면 노드를 만들어 준다. 전통적인 클러스터는 **노드 풀/그룹을 따로 만들어야** 한다.
- 어떤 라벨을 고를 수 있는지는 `kubectl describe nodes`로 본다. 파드가 어디에 떨어졌는지는 `kubectl get pods -o wide`.

### 1.2 Node Affinity와 Anti-Affinity (8.1.2)

위 nodeSelector와 결과가 같은 Node Affinity는 다음과 같다. 장점은 **표현력**이다.

```yaml
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: kubernetes.io/arch
            operator: In
            values: [arm64, amd64]       # 둘 중 아무거나
```

| operator | 의미 |
|---|---|
| `In` | 라벨 값이 목록 중 하나 이상과 일치 |
| `NotIn` | 목록 중 어느 것과도 불일치 → **Anti-Affinity**로 쓴다 |
| `Exists` | 라벨이 존재(값 무관) |
| `DoesNotExist` | 라벨이 없음 |
| `Gt` / `Lt` | 라벨 값이 정수 B보다 큼/작음(값은 문자열로 `"3"`) |

- nodeSelector의 여러 조건은 모두 만족해야 한다. Node Affinity도 **한 `matchExpressions` 안의 조건은 AND**, **`nodeSelectorTerms`가 여러 개면 OR**이다.
- **필수 대신 선호**도 쓸 수 있다. 멀티아키텍처 이미지인데 비용 때문에 Arm을 선호하는 경우다.

```yaml
nodeAffinity:
  preferredDuringSchedulingIgnoredDuringExecution:
  - weight: 100                       # 여러 선호가 있을 때 우선순위
    preference:
      matchExpressions:
      - key: kubernetes.io/arch
        operator: In
        values: [arm64]
```

**선호 규칙의 함정**

스케줄러(파드를 노드에 배치)와 플랫폼 오토스케일러(노드를 추가)는 따로 움직인다.

1. 기존 노드에 **선호하지 않는 유형이라도 남는 자리**가 있으면 스케줄러가 먼저 거기에 파드를 올린다.
2. 파드가 Pending이 아니니 오토스케일러는 선호 유형의 노드를 늘릴 **기회가 없다**.

클라우드에서는 보통 **꼭 필요한 기능만 required로 걸고, 용량은 플랫폼이 대 주길 기대하는 편**이 낫다.

### 1.3 Taint와 Toleration (8.1.3)

특수한 노드(GPU, Arm, Spot)에는 **기본적으로 파드가 안 올라오게** 하고 싶다. 다른 모든 파드에 `NotIn` anti-affinity를 다는 건 번거롭다. 대신 노드에 **Taint**를 걸고, 올라가도 되는 워크로드만 **Toleration**을 단다.

```bash
kubectl taint node <node> spot=true:NoSchedule      # 실험용. 운영에서는 노드 그룹 단위로
```

```yaml
spec:
  tolerations:
  - key: spot
    value: "true"          # operator 기본값 Equal, effect 생략 시 모든 effect와 일치
```

| effect | 동작 | 책의 의견 |
|---|---|---|
| `NoSchedule` | Toleration 없는 파드는 스케줄하지 않는다(이미 뜬 파드는 유지) | **이것을 쓴다** |
| `PreferNoSchedule` | 가능하면 스케줄하지 않는다(soft) | 목표가 "피하기"라면 soft로는 달성 못 하고 디버깅만 어려워진다 |
| `NoExecute` | 못 견디는 파드는 **이미 떠 있어도 축출** | 4절 참고 |

> 자리가 없어 Pending인 파드는 리소스를 늘리면 되지만, 엉뚱하게 특수 노드에 올라가 다른 문제를 일으키는 것보다 낫다.

**운영 환경에서는 노드 그룹 단위로 건다.** 노드는 업그레이드·복구 때 교체되므로 개별 노드에 건 Taint는 사라진다. 플랫폼의 노드 풀/그룹 API에서 Taint와 라벨을 지정한다(GKE `--node-taints`, EKS 매니지드 노드 그룹의 taints/labels). GKE 자동 모드는 Spot·Arm을 고르면 노드 Taint와 파드 Toleration을 어드미션 컨트롤러가 자동으로 맞춘다.

**Toleration만으로는 파드를 그 노드에 몰아넣지 못한다.** 허용일 뿐이라 Taint 없는 노드에도 갈 수 있다. GPU처럼 "그 노드에만, 그 파드만"이 필요하면 **Taint/Toleration + nodeSelector(또는 affinity)** 를 함께 쓴다.

**모든 Taint 허용 (DaemonSet)**

노드마다 떠야 하는 DaemonSet은 모든 Taint를 견딘다.

```yaml
tolerations:
- {effect: NoExecute, operator: Exists}
- {effect: NoSchedule, operator: Exists}
```

이러면 **현재와 앞으로 생길 모든 노드 유형에서 그 파드가 실제로 돌아야** 한다. Arm 노드가 추가됐는데 이미지가 x86 전용이면 문제다. 특정 라벨 노드만 빼려면 Toleration과 `NotIn` anti-affinity를 합친다.

```yaml
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchExpressions:
        - {key: kubernetes.io/arch, operator: NotIn, values: [arm64]}
```

### 1.4 워크로드 분리 (8.1.4)

Taint, Toleration, 라벨, nodeSelector는 **특성 선택**뿐 아니라 **워크로드끼리 노드를 나눠 쓰는 데도** 쓴다. 예를 들면 다음과 같다.

- 작업을 나눠 주는 **코디네이터 파드**와 실제 일을 하는 **워커 파드**. 워커는 수시로 늘고 줄기 때문에 안정적인 코디네이터와 **노드 오토스케일링을 분리**하고 싶다.
- **시끄러운 이웃(noisy neighbor)** 문제. 자원을 두고 다투는 두 파드를 떼어 놓는다.

노드에는 Taint와 라벨, 워크로드에는 Toleration과 nodeSelector를 건다.

```bash
kubectl taint nodes m02 group=1:NoSchedule
kubectl label node  m02 group=1
```

```yaml
tolerations:
- {key: group, operator: Equal, value: "1", effect: NoSchedule}
nodeSelector:
  group: "1"
```

| 노드 | 파드 | 결과 |
|---|---|---|
| 라벨만 | nodeSelector | 이 파드는 그 노드에만 가지만, **다른 파드도 그 노드에 올라올 수 있다** |
| Taint만 | Toleration | 다른 파드는 막지만, **이 파드가 다른 노드에도 갈 수 있다** |
| 라벨 + Taint | nodeSelector + Toleration | **전용 노드 그룹** |
| (라벨 없음) | nodeSelector | 만족하는 노드가 없어 **영원히 Pending** |

둘의 용도가 다르므로 둘 다 필요하다. 예제에서는 편의상 키-값을 같게 썼지만 같을 필요는 없다.

## 2. 파드 배치 (8.2)

복제본이 10개여도 **모두 한 노드에 있으면** 그 노드 장애로 서비스가 내려간다. 모든 노드가 한 가용 영역에 있으면 **존 장애**에도 취약하다. 어디까지 대비할지는 보장 수준과 예산의 문제이지만, **이미 가진 노드에 파드를 잘 분산하는 것은 추가 비용이 없다.**

### 2.1 고가용성 배포: topologySpreadConstraints (8.2.1)

작은 파드(100m CPU, 100MiB) 3개는 한 노드에 쉽게 들어간다. 스케줄러가 클러스터 전체에 **퍼뜨리게** 하려면 다음과 같이 쓴다.

```yaml
spec:
  topologySpreadConstraints:
  - maxSkew: 1                          # 도메인 간 파드 수 차이 최대 1
    topologyKey: kubernetes.io/hostname # 같은 값의 노드를 한 도메인으로 본다
    whenUnsatisfiable: ScheduleAnyway   # 못 맞추면 어떻게 할까
    labelSelector:
      matchLabels:
        pod: timeserver-pod             # 템플릿 라벨과 같게
```

| 필드 | 설명 |
|---|---|
| `topologyKey` | 노드 라벨 키. 호스트 이름은 노드마다 달라 **노드 단위 분산**이 된다. 존이면 `topology.kubernetes.io/zone` |
| `maxSkew` | 허용하는 불균형. 1이면 어느 노드든 다른 노드보다 **최대 1개 더** |
| `whenUnsatisfiable` | `DoNotSchedule`(안 맞으면 스케줄 안 함) / `ScheduleAnyway`(우선순위만 주고 스케줄) |
| `labelSelector` | 분산 대상 파드. 자기 자신을 가리키는 것이라 중복처럼 보여도 **직접 써야** 한다 |

- **노드에 `topologyKey` 라벨이 실제로 있는지 반드시 확인**한다. 없으면 효과가 없거나, `DoNotSchedule`이면 스케줄 자체가 막힌다.
- 테스트할 때는 규칙이 동작하는지 보이는 `DoNotSchedule`이 편하고, **운영은 `ScheduleAnyway`가 안전**하다. 복제본을 아예 못 띄우는 것보다 일단 띄우는 게 가용성 목표에 맞다.
- 배열이라 **노드 분산 + 존 분산**을 동시에 걸 수 있다.
- **스케줄링 시점 제약**이다. 파드가 뜬 뒤 노드가 추가돼도 파드는 안 움직인다. 재배치는 배포를 다시 롤아웃해(`kubectl rollout restart`) 스케줄링 규칙을 다시 태워야 한다.
- 제약 없이도 퍼져 있다면 클러스터 기본값(GKE는 노드·존 분산을 기본 제공) 때문일 가능성이 높다.

**롤링 업데이트와 `matchLabelKeys`** (스터디 보충)

기존 `labelSelector`는 새·구 ReplicaSet 파드를 한 묶음으로 센다. 그러면 롤링 업데이트 중 새 파드가 구 파드 때문에 의도하지 않은 노드로 갈 수 있다. `pod-template-hash`를 키로 추가하면 **리비전별로 따로 분산**한다.

```yaml
topologySpreadConstraints:
- topologyKey: kubernetes.io/hostname
  maxSkew: 1
  whenUnsatisfiable: DoNotSchedule
  labelSelector: {matchLabels: {app: nginx}}
  matchLabelKeys: [pod-template-hash]     # 리비전별로 분산
```

Pod (Anti)Affinity에도 `matchLabelKeys` / `mismatchLabelKeys`가 있다.

### 2.2 서로 의존하는 파드를 함께: podAffinity (8.2.2)

프론트엔드와 백엔드가 서로 자주 호출한다면 **같은 노드에 두어 네트워크 지연과 트래픽을 줄인다**. 프론트엔드에 "백엔드 파드가 있는 노드에만 배치하라"는 규칙을 건다.

```yaml
# frontend
affinity:
  podAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
    - labelSelector:
        matchExpressions:
        - {key: pod, operator: In, values: [mariadb-pod]}
      topologyKey: "kubernetes.io/hostname"
```

- 백엔드(`pod: mariadb-pod` 라벨)는 평범한 Deployment다. 프론트엔드 4개가 모두 **백엔드가 있는 노드**에 몰린다.
- `topologyKey`가 호스트 이름이면 **그 노드**, 존이면 **그 존의 아무 노드**에 올라간다.
- 백엔드 파드가 아직 없으면 required 규칙의 프론트엔드는 **Pending**이다. 필수가 부담스러우면 `preferred...`로 바꾸고 `weight`를 준다.
- 책의 조언은 **처음부터 쓰지 말고 백 포켓에 두라**는 것이다. 서비스 간 지연 시간 같은 **구체적인 문제**가 생겼을 때 꺼낸다.

### 2.3 특정 파드를 피하기: podAntiAffinity (8.2.3)

TopologySpread는 **같은 워크로드**의 복제본을 흩는다. **서로 관련 있지만 따로 배포된** 파드(예: 백엔드와 캐시)를 떼어 놓으려면 위 규칙을 뒤집는다.

```yaml
affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
    - labelSelector:
        matchExpressions:
        - {key: pod, operator: In, values: [mariadb-pod]}
      topologyKey: "kubernetes.io/hostname"
```

- 위 요소들은 **함께 쓸 수 있다**. 토폴로지 분산으로 넓게 흩고 어피니티로 세밀하게 제어한다.
- **규칙이 실제로 만족 가능한지** 확인한다. 예를 들어 "같은 앱끼리 서로 다른 노드"를 required로 걸었는데 replicas가 노드 수보다 많으면 남는 파드는 Pending이다.
- soft 규칙으로 바꿀 때는 **먼저 required로 `labelSelector`가 맞는지 검증**한 뒤 preferred로 전환한다.

### 2.4 무엇을 쓸까

| 하고 싶은 것 | 쓰는 것 |
|---|---|
| 특정 HW(Arm, GPU) 노드 고르기 | nodeSelector / nodeAffinity |
| 특정 노드 피하기 | nodeAffinity `NotIn`, 또는 노드 Taint |
| 특수 노드를 지정 워크로드 전용으로 | 노드 Taint+라벨, 파드 Toleration+nodeSelector |
| 같은 워크로드의 복제본 분산 | topologySpreadConstraints |
| 다른 워크로드와 **같은** 노드/존 | podAffinity |
| 다른 워크로드와 **다른** 노드/존 | podAntiAffinity |

## 3. 배치 문제 디버깅 (8.3)

가장 흔한 실수는 **어떤 노드에도 없는 라벨을 요구**하는 것이다(노드 없는 플랫폼에서는 플랫폼이 지원하지 않는 기능의 라벨). 이런 파드는 영원히 스케줄되지 않는다.

**규칙이 안 먹는 것 같을 때**

- 먼저 **soft(preferred) 규칙이 없는지** 본다. soft는 만족 못 하면 조용히 무시되므로 검증에 맞지 않는다.
- 노드 몇 대짜리 작은 클러스터에서 **required만으로** 동작을 확인하고, 규칙을 어기는 파드를 일부러 올려 **Pending이 되는지** 본다. 확인된 뒤 soft로 완화한다.

**파드가 Pending일 때**

스케줄러가 맞는 자리를 못 찾은 것이다. **Deployment가 아니라 파드를 describe**해야 이유가 나온다(Deployment는 복제본 수가 안 찬다는 것만 보여 준다).

```bash
kubectl get pods
kubectl describe pod <pod-name>      # Events의 FailedScheduling 확인
```

| 이벤트 메시지 | 의미와 조치 |
|---|---|
| `0/1 nodes are available: 1 node(s) had taints that the pod didn't tolerate.` | 노드 Taint를 견디지 못함. Toleration을 추가하거나 Taint 없는 노드를 늘린다 |
| `0/1 nodes are available: 1 node(s) didn't match pod affinity/anti-affinity, 1 node(s) didn't match pod anti-affinity rules.` | 어피니티/안티어피니티를 만족하는 노드가 없음. 규칙을 검토하고 수정한다 |
| `0/7 nodes are available: 1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: }, 6 node(s) didn't match Pod's node affinity/selector.` | 컨트롤 플레인 Taint + 워커는 노드 어피니티/셀렉터 불일치(`disk=hdd` 같은 없는 값을 요구한 경우) |

## 4. 보충: 스케줄러 동작과 Taint 심화 (스터디 자료)

책 8장에 더해 스터디에서 같이 본 스케줄러 동작 원리와, kind로 직접 확인한 내용이다.

### 4.1 스케줄러가 노드를 고르는 과정

```mermaid
flowchart LR
  P[파드 생성<br>인증·인가·Admission·etcd] --> F[필터링<br>조건 못 맞는 노드 제외] --> S[스코어링<br>점수 높은 노드 선택] --> B[바인딩<br>spec.nodeName 기록]
```

- **필터링(Predicates)** 으로 갈 수 있는 노드 목록을 만들고, **스코어링(Priority, 플러그인별 weight)** 으로 순위를 매긴다. **점수가 같으면 무작위**다.
- 클러스터가 크면 모든 노드를 검사하지 않고 일부만 본다(`percentageOfNodesToScore`로 조절).
- 기본 스코어링은 **LeastAllocated**(덜 찬 노드 선호)라 파드가 퍼진다. 노드를 꽉 채워 단편화를 줄이려면 **MostAllocated**를 쓰는 **스케줄러 프로파일**을 추가한다.

### 4.2 kind 실습으로 확인한 것

워커 6대에 `zone`(az1~3), `disk`(nvme/ssd), `cpugen` 라벨을 붙인 kind 클러스터로 확인했다.

| 주제 | 확인한 내용 |
|---|---|
| `IgnoredDuringExecution` | 스케줄링된 뒤 조건이 깨져도 **파드는 그대로 돈다**. 스케줄러는 배치 시점만 제어한다. 사후 재배치는 **Descheduler**(`LowNodeUtilization`, `RemoveDuplicates`, `RemovePodsViolatingInterPodAntiAffinity` 등) |
| AND / OR | 한 term 안의 `matchExpressions` 조건은 AND, `nodeSelectorTerms` 여러 개는 OR |
| `Exists` | 값 없이 키만 지정 |
| `NoSchedule` | Taint 전에 떠 있던 파드는 **유지** |
| `NoExecute` | 못 견디는 파드는 **축출**(이벤트 `TaintManagerEviction`) 후 다른 노드에 재생성 |
| Toleration 일치 | `key=value:effect` 중 **빠진 항목은 와일드카드**. `operator: Exists`만 쓰면 어떤 Taint든 통과 |
| `tolerationSeconds` | `NoExecute`를 지정한 시간만 허용(30초 뒤 축출 확인) |
| `cordon` | 노드에 `node.kubernetes.io/unschedulable:NoSchedule` Taint가 붙는 것과 같다 |

**노드 장애 시 자동 Taint**

| effect | key | 의미 |
|---|---|---|
| `NoExecute` | `node.kubernetes.io/not-ready` | 노드가 Ready가 아님 |
| `NoExecute` | `node.kubernetes.io/unreachable` | 노드와 통신 불가(Unknown) |
| `NoExecute` | `memory-pressure` / `disk-pressure` / `pid-pressure` | 자원 부족 |

- 파드는 기본으로 `not-ready`와 `unreachable`에 **`tolerationSeconds: 300`** 이 붙어, 5분 안에 복구되지 않으면 축출된다. 더 오래 버티게 하거나 중요 파드는 직접 명시한다.

## 정리하며

- 노드 선택은 **nodeSelector → nodeAffinity**로 표현을 넓히고, **기본 접근 차단은 Taint**, **허용은 Toleration**이 맡는다. 전용 노드는 **Taint + 라벨, Toleration + nodeSelector**를 짝으로 건다.
- 선호 규칙과 `PreferNoSchedule`은 기대와 다르게 동작하기 쉽다. **꼭 필요한 조건은 required**로 걸고 용량은 플랫폼에 맡긴다.
- 복제본은 **topologySpreadConstraints**로 노드·존에 분산한다. 운영은 `ScheduleAnyway`, 롤링 업데이트가 신경 쓰이면 `matchLabelKeys: [pod-template-hash]`.
- 파드 간 Affinity/Anti-Affinity는 **구체적인 문제가 있을 때** 꺼낸다. required로 걸 때는 만족 가능한지 먼저 센다.
- 배치 규칙은 **스케줄링 시점에만** 적용된다. 이후 변화는 롤아웃이나 Descheduler로 보정한다.
- DevOps 입장에서 챙길 곳은 **`topologyKey` 라벨이 실제 노드에 있는지, Taint/라벨을 노드 그룹 단위로 관리하는지(노드 교체 시 유실), DaemonSet이 모든 Taint를 견딜 때 신규 노드 유형(Arm 등)에서 정말 도는지, Pending 파드의 `FailedScheduling` 이벤트 알림**이다.
- 7장 Kubeflow Notebooks의 Affinity/Tolerations 선택지는 이 장 규칙으로 만든다. 고성능·GPU 노드를 정말 막으려면 어피니티만으로는 부족하고 **Taint + Toleration**을 함께 쓴다.
